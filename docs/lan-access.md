# Доступ к локальной сети при включённом VPN

Практический документ: что делать, если VPN нужен, но локальные адреса (роутер, ноутбук, принтер, локальный dev-сервер) должны открываться напрямую. Поведение описано по коду [VpnService.kt](../app/src/main/java/io/nekohasekai/sagernet/bg/VpnService.kt) и [ConfigBuilder.kt](../app/src/main/java/io/nekohasekai/sagernet/fmt/ConfigBuilder.kt); сценарий проверен владельцем на физическом смартфоне с включённым VPN.

## Почему по умолчанию не работает

При выключенном обходе в туннель забирается весь IPv4-трафик:

```kotlin
builder.addRoute("0.0.0.0", 0)
```

Поэтому запрос к `192.168.1.10`, `10.x.x.x` или `172.16–31.x.x` тоже уходит в VPN-интерфейс, а не в Wi-Fi/Ethernet. Локальный сервер при этом либо недостижим, либо соединение уходит на удалённую сторону туннеля.

## Что включать

Настройки → раздел **маршрутизации**:

| Переключатель | Ключ | Что делает |
|---|---|---|
| **Bypass LAN** | `bypassLan` | Меняет набор маршрутов `VpnService`: вместо `0.0.0.0/0` в туннель добавляются только публичные диапазоны, а частные остаются вне VPN на уровне системы. |
| **Bypass LAN in Core** | `bypassLanInCore` | Добавляет в конфиг ядра правило `ip_is_private → bypass`, чтобы частные адреса не отправлялись в прокси/апстрим. |

Оба параметра перезапускают сервис при изменении — VPN нужно поднять заново. Для прямого TUN-режима достаточно первого; если приложения ходят через локальный прокси-порт, нужны оба.

## Что именно остаётся вне туннеля

Проверено по списку `bypass_private_route` из ресурсов (155 публичных CIDR):

| Адрес | Идёт в туннель |
|---|---|
| `10.76.41.155` (частный `10/8`) | нет |
| `172.22.12.76` (`172.16/12`) | нет |
| `192.168.1.10` (`192.168/16`) | нет |
| `100.64.0.1` (CGNAT) | нет |
| `169.254.1.1` (link-local) | нет |
| `127.0.0.1` (loopback) | нет |
| `8.8.8.8` (публичный) | да |

То есть обход покрывает все частные, CGNAT, link-local и loopback адреса, а не только «свою» подсеть.

## Чего обход не делает

- **не пробрасывает порты** и не делает сервис доступным извне: он только не заворачивает локальный трафик в туннель;
- **не обходит изоляцию клиентов** на точке доступа и **файрвол** другой машины — если телефон не видит ноутбук на уровне L2/фильтра, обход не поможет;
- **не резолвит** имена `*.local`/mDNS за вас — обращайтесь по IP;
- **не трогает** TLS, REALITY, пиннинг сертификатов и другие гарантии безопасности;
- не относится к функции [поиска LAN-прокси](lan-discovery.md) — это отдельный ручной поиск слушателей в сети.

## Как проверить

1. Убедиться, что сервис на другой машине слушает не только `127.0.0.1` (например, `ss -ltnp` → `0.0.0.0:PORT`).
2. Открыть адрес с телефона **без VPN** — базовая проверка сети.
3. Включить **Bypass LAN** (+ **Bypass LAN in Core**), перезапустить VPN, открыть тот же `http://<частный-ip>:<порт>`.

Обратный тест тоже показателен: при выключенных обходных переключателях тот же адрес перестаёт открываться — значит трафик действительно уходил в туннель.

## Типичные ошибки

| Симптом | Причина |
|---|---|
| Работает без VPN, не работает с VPN | не включён обход LAN |
| С Windows/другого хоста работает, с телефона нет | разные сети либо изоляция клиентов на точке доступа |
| Порт открыт, но ответ 400/403 | сервер проверяет заголовок `Host` (dev-серверы вроде Vite) |
| Адрес меняется после перезапуска WSL/контейнера | меняется IP виртуальной сети, нужен проброс/правило на актуальный адрес |

## Адрес прокси для клиентов в сети (ТВ и настройки)

Когда включена опция **«Разрешить подключения из локальной сети»** (`allowAccess`), mixed-инбаунд слушает `0.0.0.0:<mixedPort>` — по умолчанию порт 2080, протоколы HTTP и SOCKS5. Адреса, которые вводят клиенты, TunXBox показывает сам.

### Какие адреса показываются

**Все IPv4-адреса всех поднятых интерфейсов, кроме loopback.** Приложение не угадывает, какой из них «локальный»: один и тот же телефон может получать адрес по 4G и раздавать интернет по Wi-Fi, работать через Ethernet, tethering, несколько сетей или VPN — доступность адреса определяется сетью клиента, а не устройством. Поэтому список полный, а различить адреса помогает имя интерфейса в подсказке.

- IPv6-адреса не показываются: инбаунд привязан к IPv4 `0.0.0.0` и такие подключения не примет. Это ограничение протокола, а не фильтр «локальности».
- Адреса опущенных (down) интерфейсов не показываются: по ним нельзя подключиться.
- Дубликаты (один IP на двух интерфейсах) схлопываются, остаётся первый.
- Порядок: `wlan*`, затем `eth*`, затем точка доступа (`ap*`, `swlan*`, `softap*`), затем остальные (мобильные, туннель) по имени интерфейса. Порядок — подсказка, а не решение за пользователя.

### Плитка на ТВ

При состоянии **Connected** и включённом доступе из LAN второй плиткой ряда **Connection** появляется карточка «Прокси в локальной сети»: каждый адрес — отдельной строкой `IP:порт`.

- Плитка имеет **тот же размер, что и остальные плитки ряда** (`TvCardMetrics`): та же ширина в px и та же высота. Список адресов занимает высоту, оставшуюся от подписи и пояснения, и делит её между адресами, поэтому четвёртый-пятый адрес уменьшает авто-размер строк, а не делает плитку выше соседних. Раньше ширина задавалась в dp как пиксели, и на 1080p-ТВ (плотность 2.0) плитка была вдвое уже остальных, а высота росла с каждым адресом.
- Строка адреса **не обрезается**: одна строка, авто-размер 11–22 sp, без многоточия. Самый длинный вариант `255.255.255.255:65535` (21 символ) помещается целиком; подпись и пояснение — отдельными строками и могут сокращаться.
- Плитки нет, если VPN не подключён, доступ из LAN выключен или у устройства вообще нет IPv4-адресов, кроме loopback. Заглушек `0.0.0.0` не бывает.
- OK открывает подсказку со всеми адресами и именами интерфейсов (`192.168.43.1:2080 (wlan0)`), чтобы было видно, откуда каждый адрес.

### Настройки

В разделе **Inbound Settings** у переключателя «Разрешить подключения из локальной сети» подпись меняется на **«Клиенты в сети: 192.168.43.1:2080, 10.76.41.155:2080»** — все адреса через запятую. Пересчитывается при включении, при изменении порта и при возврате на экран (`onResume`), поэтому смена Wi-Fi/Ethernet не оставляет устаревший адрес. Если IPv4-адресов нет — «Нет адреса локальной сети — подключите Wi-Fi или Ethernet».

### Границы

- Показываются адреса, а не проверка доступности: приложение не проверяет, дойдёт ли до него клиент из своей сети (изоляция клиентов на точке доступа, файрвол, NAT оператора — вне его контроля).
- Плитка и подпись информируют, но **не включают** доступ и **не открывают порт** наружу: это делает только опция `allowAccess`.
- Список обновляется при следующем обновлении экрана/плитки (короткий кэш), без фонового опроса.
