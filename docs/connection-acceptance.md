# Повторная проверка Hysteria2 и TLS на rc158

## Что известно, а что нет

- [Issue6](https://github.com/LeonidYasin/TunXBox/issues/6): прежний physical report — Hysteria2 то работает, то не передаёт трафик, иногда медленно. Причина не установлена; свежая проверка rc158 не получена. Исправленный ранее истёкший сертификат мешал загрузке подписки, но это не доказанная причина нестабильности VPN.
- [Issue10](https://github.com/LeonidYasin/TunXBox/issues/10): в rc148 «Автовыбор»/«Швеция» сообщали NET_TIMEOUT/NET_TLS_TRUST на URL_TEST, Happ работал на той же приставке. Сеть и конкретный выбранный участник Auto ещё требуют одинакового сравнения. Новый NET_BUSY fix и улучшенная диагностика не доказывают исправление исходного подключения.
- TLS проверяется в разных местах: HTTPS загрузка подписки; TLS/QUIC соединение с прокси; HTTPS запрос к URL-test destination через прокси. Код URL_TEST/NET_TLS_TRUST сам по себе не определяет, чей сертификат не принят. Standalone Android TLS probe не равна TLS в Go core, REALITY/uTLS или проверке proxy authentication. [Границы диагностики](connection-diagnostics.md).

## Минимальная проверка владельцем — сначала без новых настроек

1. Указать модель устройства, Android, версию TunXBox/ABI и версию Happ. Ожидаемый опубликованный APK — rc158, versionCode48000158, source0bd5770. Номер приложения не подменять HEAD ветки разработки.
2. Взять один конкретный проблемный узел, не общий Auto selector. Сопоставление выполняется локально; не присылать его адрес/имя/ключи. Если невозможно определить выбранного участника Auto, отметить сравнение как несопоставимое.
3. На одном устройстве и той же Wi-Fi/Ethernet/мобильной сети последовательно проверить TunXBox и Happ, не запуская конкурирующие VPN одновременно. Не менять сертификаты, SNI, MTU, DNS, obfuscation и transport между попытками. Проверку сертификатов не отключать; если reference уже допускает insecure, это не strict-TLS baseline.
4. Для каждого клиента отметить: VPN стартовал ли; открываются ли обычные сайты; есть ли передача данных; сколько времени до отказа. Ноль байт в простое не считать ошибкой. Один успешный запуск не опровергает intermittent report; начать с трёх коротких повторов, без скрытого throughput/download теста.
5. При отказе TunXBox открыть полный отчёт и вручную «Расширенная проверка» в TV-интерфейсе. Она ограничена по времени, отменяется, не переключает VPN/профиль. Экспортировать встроенную безопасную TXT/QR сводку, а не конфигурацию или raw log. Если экрана/кнопки нет, сообщить версию и режим, не придумывать результат.
6. Только после исходного сравнения менять один фактор за раз: другая доступная сеть, foreground/возврат после screen-off. Записать, какой фактор изменён. Не запускать порт-сканирование и не публиковать данные сети.

## Форма безопасного результата

```text
TunXBox version/code/commit (из встроенного отчёта):
Модель / Android / ABI:
Happ version:
Транспорт: Hysteria2 либо VLESS/TCP/TLS (без адреса):
Сеть: Wi-Fi / Ethernet / mobile (без SSID/IP):
Тот же конкретный узел в обоих клиентах: да / нет / неизвестно
Проверка сертификатов включена в обоих: да / нет / неизвестно
TunXBox: VPN старт / обычный трафик / короткие повторы успешно-всего:
Happ: VPN старт / обычный трафик / короткие повторы успешно-всего:
Сбой: сразу / через ___ / после возврата / не воспроизведён
Безопасный код и этап из отчёта:
Расширенная проверка: завершена / отменена / недоступна
```

Не включать subscription URL, имена провайдеров/профилей, hosts/IP, SNI values, UUID, пароли, ключи, исходный JSON/URI, сырые сообщения ядра или screenshot с конфигурацией. Не требуется передавать доступ к серверу. Отчёт проверить перед отправкой; публичный issue не место для секретов.

## Следующий шаг разработчика

При воспроизведении — локализовать этап, проверить importer→bean→outbound (SNI/ALPN/flow/fingerprint/CA), физическую привязку, trust-store и различия ядра. Для Hysteria2 отдельно учитывать QUIC/UDP, authentication/obfs и сеть, но не назначать их виновником без доказательства. Создать синтетический regression fixture и целевой patch; повторить исходный physical сценарий. При отсутствии воспроизведения — записать точные границы, а не закрывать intermittent report за один pass. Дальнейший native peer/stage tracing должен сохранять whitelist и требовать отдельного review; автоматические uploads/TLS bypass запрещены.

Решение release scope — явное fix или согласованное documented defer. Никакое количество offline/emulator smoke не заменяет это сравнение. Исследование extended/Xray относится к issue13 и не является исправлением #6/#10.
